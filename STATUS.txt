Current Activity:
API run requests sharing a database are serialized by an expiring row lock, and active task/run leases are heartbeated by the orchestrator. Independent worker processes and same-project worktree isolation are not yet implemented.

Recently Completed (most recent first):
- Bounded parallel execution: the orchestrator now claims a bounded independent batch, commits leases before work, runs executor calls in a bounded `ThreadPoolExecutor` (one worker at cap one; parallel only above one), renews active leases and applies task state changes on the main session/thread. Each worker uses its own SQLAlchemy session; same-project tasks do not run together because they may mutate one workspace. Barrier and heartbeat tests prove overlap, session isolation, same-project exclusion, failure isolation and renewal during long work. A GitHub Actions workflow now defines backend and frontend validation; remote execution is not yet observed.
- Opt-in adaptive dispatch cap: `AATM_ADAPTIVE_CONCURRENCY` applies the local CPU/memory/disk recommendation to the per-run dispatch budget, never above `AATM_MAX_CONCURRENCY`. Existing running tasks are deducted; zero free slots claims no work. Same-process run requests serialize. Status API and Operations UI expose the mode and cap. Parallel execution and lease heartbeats run within one orchestrator pass; API run requests sharing a database serialize across processes. A distributed multi-worker scheduler remains unimplemented.
- Advisory provider-budget notifications: in-app feed now surfaces persisted usage at/above 80% of a positive scoped limit in English/Arabic/Persian; threshold does not alter the hard guard. Tests cover at-threshold, below-threshold, zero-limit and allowed-under-cap behavior.

Two real defects fixed — cancellation could never reach a running task (write transaction held across the run → "database is locked", now committed first + SQLite WAL), and a stale cancel flag left stopped tasks in `running` forever (now refreshed).
